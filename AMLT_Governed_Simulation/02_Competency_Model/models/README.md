# Competency Model Artifacts

This folder contains all structured competency model artifacts used by the AMLT Governed Simulation system.

These artifacts are upstream governance anchors for simulation evaluation and LMS completion logic.

---

## Artifact Types

There are two types of competency model artifacts stored here:

### 1️⃣ DRAFT Models

**Filename format:**
AMLT_CM_vX.Y_DRAFT.json


**Status inside JSON:**
"status": "DRAFT"


Purpose:
- Generated by CM_DRAFT prompt
- Intended for SME review and refinement
- May be edited or overwritten during iteration

Characteristics:
- May contain open questions
- May contain traceability gaps
- Not valid for runtime evaluation
- Not governance-binding

Draft models must never be referenced directly by the simulation runtime.

---

### 2️⃣ LOCKED Models

**Filename format:**
AMLT_CM_vX.Y.json


**Status inside JSON:**
"status": "LOCKED"


Purpose:
- Generated by CM_COMPILER_LOCK prompt
- Schema-validated and normalized
- Approved by SME
- Versioned and immutable

Characteristics:
- Contains required traceability for every competency
- Meets structural and validation rules
- Approved and signed off
- Safe for runtime consumption

Only LOCKED models may be referenced by:
- Simulation Runtime
- Governance Validator
- LMS completion logic

---

## Versioning Rules

Version format:
MAJOR.MINOR


- MAJOR: Structural change to competencies
- MINOR: Refinements to definitions or indicators

Example:
- AMLT_CM_v1.0.json
- AMLT_CM_v1.1.json
- AMLT_CM_v2.0.json

LOCKED models must never be overwritten.
New changes require version increment.

---

## Change Governance

Each LOCKED model should be accompanied by an entry in:
/02_Competency_Model/traceability/AMLT_CM_change_log.md


Change log entries should include:
- Version number
- Date
- Summary of changes
- Approved by
- Rationale

This ensures audit traceability.

---

## Runtime Dependency

Simulation runtime should reference a specific locked model version:

Example: competency_model_id: AMLT_CM_v1.0


Runtime must not dynamically alter competencies.
Competency evaluation must always reference a fixed, locked model.

---

## Architectural Principle

Competency modeling is upstream from simulation.

Meaning:

Corpus → Draft Model → SME Approval → Locked Model → Simulation Runtime → Governance Validation → LMS Completion

This separation ensures:

- Determinism
- Auditability
- Stability
- Governance integrity

---

If you are unsure which model version to use, do not guess.
Check the runtime configuration or consult the change log.
